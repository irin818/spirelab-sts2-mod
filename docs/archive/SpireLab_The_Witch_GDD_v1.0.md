# SpireLab / 魔女（The Witch）完整角色 Mod 规格书 V1.0

> **交付定位：** 用于 Codex 在现有 SpireLab 私有仓库中实现一个原创、可选择、可从头通关《杀戮尖塔2》主线的角色 Mod。本文是设计规格和待验证的平衡基线，不是已编译的代码，也不是已实测的最终平衡结论。
>
> **版本基准：** macOS Apple Silicon；Steam 正式版 STS2 v0.111.1；C# net9.0；MegaDot 4.5.1-m.14 Mono；BaseLib 3.4.8；以当前本地 API 实证为准。严格保留现有工程、Git 分支/PR 流程与已有 Phase A 成果。
>
> **用户已经确认的不可改核心：** 角色为黑发红挑染的冷漠哥特魔女，镜中映出相反人格；魔法启迪是固有被动、从本局已经获得的牌中随机转化；欲望只有《堕落自信》《原初贪婪》《怠惰》《灾祸之源》《狂赌之渊》五张；镜中人具有生命逆转和持续反伤；支持困难但真实存在的无限流可能；美术必须是原创高完成度日式动漫风，参考《电锯人》的黑红强反差、电影感和情绪张力，而非临摹角色。

## A. 产品目标与完成定义

- 游戏体验定位：独特但不过强的原版级卡牌构筑角色，不依赖某一张稀有牌才能生存。三个普通构筑轴（魔药、镜子、魔法书）与五张高风险欲望牌交叉；强力组合应有获取和构筑成本。原版级而非纯数值碾压。
- 完整池：4种基础牌定义（初始牌组共10张） + 20普通 + 38罕见 + 27稀有 + 2古代 = **91种卡牌定义**。注意基础牌“定义数”不等于起手组张数。5张欲望全部计入85张奖励牌，不再新增任何带欲望标记的卡。
- 专属遗物：初始、初始古代升级、1普通、2罕见、3稀有、1商店，共9件；专属药水3种（普通/罕见/稀有）。提供人物立绘、全部卡面、图标、能量/UI资源、动画与音效；完成游戏内剧情对话、卡牌百科和简中/英文基础本地化。
- 单人正式版先完成完整验证；联机的同步、分支 API、资源兼容需要独立验证，不得声称未经测试的联机功能已支持。
- 先做可玩垂直切片，验证乐趣与不变量，再实现全部卡池。即使自动化 AI 能生成全部代码，也不得跳过中间实际编译和游戏内测试。

## B. 视觉设定与角色身份

- 中文名：**魔女**；英文名：**The Witch**（可在本地化定稿时微调）。人物设定：神情冷漠、克制的年轻女性，黑色中长发，局部深红挑染，细长眼形，黑红宫廷哥特礼服；非真实人物、非既有动画角色。
- 永久随身物：华丽但破损的全身立镜（银黑镜框、细密裂纹）；镜中同一少女呈轻蔑、活泼或危险的神情，有相反动作和近似独立人格的表现。
- 三体系美学：魔药=炼金瓶、暗紫与深金火焰；镜子=冰银、破碎玻璃、灰蓝镜光；欲望=猩红、漆黑、刺状纹样和不对称构图；魔法书=古老羊皮纸、浮动咒文、深金纹章。统一黑红主色，绝不将它们做成四套不一致的画风。
- 动画气质：成熟日式二维动画，精致轮廓、干净上色、局部粗线条、硬边高反差阴影，电影式特写/逆光/运动镜头，妖异但清晰；低饱和环境配局部高饱和红。参考《电锯人》所呈现的视觉语言，但**不要复制其中任何角色、脸型组合、服饰设计、标志物、镜头、完整画面或 Logo**。
- 三视图/统一角色设定先做：正、侧、背、服饰近景、脸部表情、镜中表情差异、标准武器/道具、色卡、背景比例关系。全部卡图以确定后的设计为参考，防止不同生成轮次人物漂移。

### 生成式美术生产要求

1. 所有图片必须为原创视觉。参考作品仅用于概括视觉特征，不直接提示模型复制特定角色或画师画法。
2. 先做可确认的角色立绘、镜像双人构图、卡牌模板与3张不同体系的标准卡图（style anchors），通过后才批量扩展。
3. 图片生成如当前 Codex 环境没有可用能力，则使用占位图并维护资源清单，不能声称已经生成美术；可将素材需求移交给具备图像生成工具的工作流。
4. 图片内不让 AI 生成卡牌文字、价格或数值；文字由游戏 UI 本地化绘制。大多数卡牌主体必须适合窄画框裁切，视觉焦点明显；不要全部采取复杂人物全身像，允许静物/符文/场景/动作特写。
5. 以当前角色模板实际规格和导入路径为准。社区文档参考：普通卡图1000×760或500×380 PNG；古代牌606×852；遗物小图及描边94×94、大图256×256；能力图标64×64及256×256；药水与轮廓256×256。以实际项目验证最终尺寸与命名。
6. 工程内保存资源源文件、生成提示词、授权/来源、用途、审核状态与导出 PNG；仅把能够合法分发的文件打包发布。

## C. 游戏规则、状态与角色定位

### C1. 开局与基础参数

- 最大生命：**68**（测试起点；后续可在66–72之间平衡）。每回合基础能量3，每回合基础抽牌5 + 固有被动额外1 =6。
- 初始金币依照游戏默认值；保留原版地图、敌人、事件、商店、解锁规则及伤害结算方式。
- 初始牌组10张：打击·魔女×4、防御·魔女×4、薄镜守护×1、初配药剂×1。
- 初始遗物“破损梳妆镜”：每场战斗首次实际使用魔法启迪转化时获得3点格挡。注意它只是固有被动的轻量补充，不提供额外的抽牌和能量。
- 属性、初始遗物与被动分开实现；固有被动不得依靠持有初始遗物才激活。失去初始遗物后被动仍生效。

### C2. 魔法启迪（固有、每回合）

**效果：** 每回合开始，按现有游戏流程完成原本的5张抽牌并额外抽1张；随后至多选择1张手牌替换成随机的本局已获得卡牌，可跳过，耗费0能量。若手牌已满，须按原版手牌容量规则处理，不能造成 UI 卡死。

**采样池：** 本局当前永久牌组中的实际卡牌副本等权采样；相同名称有多个副本则权重相应增加。允许打击、防御、角色牌、无色牌、古代牌和永久牌组中已有的诅咒；排除仅本场临时生成的状态、Token、未实际获得的奖励、历史获得但已删除的牌。抽到不可打出的卡属于随机代价，不应强行剔除。选中的来源卡可被抽为“同名其他副本”。

**防止免费删牌/无限复制的实现语义：**

- 选中的源手牌进入临时保管槽；立即生成一个**临时替身牌**在相同手牌位置，本回合按其卡牌正常消耗能量/触发打出和相关状态。
- 替身牌若打出、被弃置、被消耗或以其他方式离开手牌，移除替身对象并把原始来源卡送入弃牌堆。否则，在本回合结束时强制清理替身并把源卡送入弃牌堆。**无论如何不得在一回合内通过启迪永久减少牌组大小或永久增加牌组大小。**
- 替身是战斗临时牌，不改变地图外永久卡组；原牌的升级/附魔状态不能永久丢失；新牌继承其采样到的实际副本的升级/附魔状态（不继承来源牌的数值）。
- 替身若为可重复回手卡（例如狂赌之渊），本回合内允许回手反复使用；结束回合时仍必须清理替身并恢复源牌。变为能力牌并打出时，能力持续存在，但来源牌仍恢复到弃牌堆。
- **本场对同一张手牌再次使用其他转化效果时，必须追踪并正确释放原来源卡**；不能制造悬空对象、丢失永久卡或卡牌无限复制。
- “使用过魔法启迪”的计数：每回合实际执行了选择且成功换牌才计1，跳过不计；与打出牌、抽牌、弃牌、消耗分别是不同事件。
- 如以上“替身牌生命周期”与当前引擎 API 不兼容，先由 Codex 提出同等保真且不引入免费删牌的替代设计，附实测和最小复现；不得静默改变规则。

### C3. 体系标签

- 魔药、镜子、魔法书是**策划分类/画面主题标记**，默认没有独立减费、被动加成或资源条。只有具体卡面明确写出的条件才触发。
- **欲望是唯一特殊机械标记**（Desire）。只允许标记五张指定卡：堕落自信、原初贪婪、怠惰、灾祸之源、狂赌之渊。普通牌和其他体系卡绝不新添 Desire 标签。
- 为所有卡建立唯一、稳定的 Card ID，避免使用中文显示名称作为内部序列化键。升级不能改变唯一 Card ID。

### C4. 数值与事件术语

- **真实生命（Real HP）**：用于生命献祭、支付代价、是否低于最大生命一半、永久治疗与战斗结束后的保存。当前真实生命不能通过不可支付的献祭降为0。
- **镜像生命（Mirror HP）**：战斗内临时承伤缓冲，先于真实生命承受穿过格挡的敌方伤害；不计入支付生命代价，不计作回复或提高最大生命，不通过普通治疗恢复，战斗结束移除。游戏 UI 要分段显示“真实/镜像”，对外显示战斗有效生命 = 两者之和。
- “低于一半”严格按 `2 × RealHP < MaxHP` 判定；恰好一半不算。
- “额外获得能量”指卡牌/遗物/Power 增加的能量，不包含每回合默认重置的3点；跨回合效果给予的能量属于额外获得。触发型加能量必须设置事件源、防递归与次数记录。
- “剩余能量”按回合结束瞬间实际剩余数值判断，包含魔力之巅所保留的能量；能量上限遵循引擎有效范围，必须测试溢出。
- 反射伤害：以实际被玩家格挡吸收的**敌方攻击伤害**为基准，向攻击者造成非攻击来源的伤害，正常考虑敌人的格挡、无敌等防护；不受玩家力量或虚弱的攻击修正、不反射已经反弹的伤害、不触发反射递归。若有多种独立反射来源，分别结算并以约定顺序统一向下取整。生命代价/直接失血、攻击免疫部分与未被格挡部分均不触发反射。
- 敌方每段攻击单独计算格挡与反伤；一回合多敌人攻击需正确识别发起者；反弹时敌人死亡不造成战斗流程卡死。
- “免疫下一次敌方攻击”只抵消一次攻击实例，不免疫支付生命、诅咒、状态损血或非攻击伤害；免疫生效后不算格挡成功，因而不产生反伤。持续窗口到自己的下回合开始，除非先使用。
- “消耗”指本场战斗一次性离开可循环卡组（Exhaust），不等于从永久牌组删除；能力牌在打出后常驻效果不需要再添加消耗。
- “印刷费用”指原始未被各类减费机制影响的卡面费，用于条件判断；实际支付按游戏统一费用管线计算。费用减免最低为0，不额外返还差额能量。
- 对每回合首次、下一回合、上一敌方回合等条件提供统一记录器，回合转换时重置；联机须使用确定性事件源与相同随机流。

### C5. 镜中人（最高优先级专项机制）

- R10《镜中人》为3（升级2）费稀有能力；仅**第一次**本场战斗打出时触发生命逆转，再次被生成/打出不再逆转且不叠加50%反伤。
- 发动前 `R = RealHP`, `M = MaxHP`; `Target = max(1, M - R)`。如果 `Target > R`，增加 `MirrorHP = Target - R`；如果 `Target < R`，永久扣除 `R - Target` 真实生命；如果相等则只开启反伤。发动前已有镜像生命时，将旧镜像生命先清除，再用真实生命计算本次逆转（但镜中人默认只能触发一次）。
- 例：M70/R20 → 战斗有效HP50（真实20+镜像30），战斗结束最多仍保留真实20；M70/R50 → 真实HP降为20，无镜像生命；M70/R70 → 真实HP降为1（不是0）。
- 镜像生命受敌方伤害先于真实生命减少；玩家主动支付的生命代价只从真实生命扣；常规治疗只能恢复真实生命且不超过最大HP，不能将战斗有效生命无限叠加超过最大HP（治疗时若有镜像，则必要时按有效生命上限截断新增镜像或治疗值，以不突破 M）。
- 形态开启后，全场反射实际被格挡吸收的敌方攻击伤害的50%，向下取整；额外反伤卡可继续叠加其来源，但镜中人自身不叠加。
- 镜像生命显示应与真实生命分层、可读；死亡判定在 RealHP+MirrorHP 均为0时生效；一切不能由镜像生命支付的代价必须严格先验证而后执行。
- **重要平衡风险：** 《狂赌之渊》能快速降低真实生命，再用镜中人换取大量镜像生命，作为高风险单战防护可以保留；但镜像生命不抵偿下局真实生命，不能成为每战免费全额治疗。

### C6. 五张欲望牌的统一规则

- 堕落自信：3（2）费、能力；本战欲望牌费用-1，**不可叠加**；已有同名能力时再次打出不会额外降费。它作用于以后生成和当前手牌中的欲望牌，最终费用最低0。
- 原初贪婪：2（1）费、技能、消耗；把其余手牌洗入抽牌堆并抽5。自身不洗回；作用于临时替身时正确处理其源卡。
- 怠惰：2费、技能；正常获得10（12）格挡并结束回合；若为该回合第一张实际打出的牌则**改为**获得一次敌方攻击免疫而不是格挡，随后结束回合。升级只改格挡数。
- 灾祸之源：2费、稀有技能、消耗；从其余四种欲望卡中不重复地随机给出2（3）个选项，选1张在手牌生成临时副本，**仅本回合费用为0**。不生成自身；临时副本不进永久牌组；第4种不在升级版保证出现；如无有效选择时给出安全降级行为并记录日志。
- 狂赌之渊：1费、稀有技能；失去 `ceil(RealHP×50%)`（升级40%）的真实生命，抽1，获得2能量，返回手牌。若损血值≥真实生命则不能打出；生命损失不被格挡或镜像生命抵消；每次支付最少1点；可被堕落自信减到0费。允许反复出牌，但并非无代价无限流；任何外部回血组合必须专项压力测试。
- 全部欲望卡仅有上述五种；不得新增任何 Desire 普通牌、低费欲望抽牌组件或隐藏欲望资源条。

## G. 结构性平衡及无限流规则

### G1. 角色强度意图

- 初始被动每回合6张牌及免费替换非常强，因而初始生命暂设68、初始遗物较轻，基础牌数值不显著超过原版。不要再给予免费的常驻额外能量。
- 普通牌需确保没有《镜中人》《魔力之巅》《堕落自信》时，仍能提供足够的攻击、防御、过牌与能量转换。高费用牌必须在适当构筑中有可用性。
- 狂赌之渊是主要“以生命换能量”的稀有手牌循环器；**低费回血卡全部消耗**，不提供任何可无成本重复的永久治疗引擎。
- 不应机械限制无限流次数或直接禁止无限流。应该通过构筑条件、循环资源守恒、有限消耗组件、获得难度和生命风险来保证其门槛。
- 魔法启迪不能免费永久删牌、复制能力卡到永久牌组或每回合以同一种稀有卡为确定目标检索。
- 欲望只有5张；全体减费只影响有 Desire 标记的卡，且只能-1不可叠加。

### G2. 组合压力测试

| 组合 | 期望玩法 | 必测失败模式 |
|---|---|---|
| 魔法启迪+欲望稀有卡 | 偶尔复制高价值临时牌 | 每回合稳定复制稀有能力/源卡丢失/悬空引用 |
| 堕落自信+狂赌之渊 | 0费多次失血换资源，短回合爆发 | 1HP继续打出/越界生命/无限回手线程 |
| 狂赌之渊+回复+灵药瓶 | 有限回血支撑爆发 | 同战不消耗回血造成轻易无限能量 |
| 狂赌之渊+镜中人 | 低真实HP转换为单战镜像HP | 镜像HP支付血费/战后变成永久治疗 |
| 魔力之巅+魔力倾泻 | 积攒高能量X费终结 | 大能量整数溢出/多段伤害爆炸/冻结 |
| 镜中人+裂面+反光刻印+镜葬 | 同一敌人多段格挡反射 | 重复错误计数/反射递归/死亡异常 |
| 空镜+万象镜厅 | 大额格挡协同 | 百分比加成互相递归或取整不稳定 |
| 原初贪婪+魔法启迪 | 高价值洗牌与随机重构 | 生成牌被洗走后原始牌永久消失 |
| 逆序典礼+0费牌 | 强力过牌，但一次/回合 | 自触发无限抽牌 |
| 灾祸之源+堕落自信 | 早期的强力随机免费欲望 | 被动减费重复、灾祸自我生成、免费卡永久改费用 |

### G3. 数据验证方法

- 本方案85张奖励牌默认均可在单人模式获得；原版同规模数据含部分联机限定牌，因此本方案单人有效池略大于原版。完整性优先；若后续数据表明稀释奖励池影响构筑，必须通过实测与用户确认再调整，而不是未经授权删牌。
- 用静态检查验证85奖励牌唯一 ID、稀有度20/38/27、欲望恰好5种、所有卡带升级文本与机制实现、无重复/失效资源路径。
- 用组件测试验证生命与能量支付的上下界、镜像HP、反射、技能消耗、复制/替身生命周期、回合触发次数。
- 用有限状态搜索/循环检测探测低费小牌组中的**非递减资源闭环**：如果能在回到同样可操作手牌/弃牌状态时，能量、真实HP都不减少，并重复造成伤害或增加格挡，则标记为可能无限。不要因为存在无限就一律判不合格；分析所需关键卡数量、升级/遗物条件以及能否第一幕轻易成立。
- 用不同种子、怪物、首领、遗物组合和不同阶段牌组进行整局测试。与原版同难度同种子对照时注意不同角色的奖励池会改变随机序列，故按相似规则、多个种子、相似测试样本比较，而不是单次通关对比。
- 建议初期先跑10–20场快速人工测试定位规则问题，再用更多自动模拟统计；不要把未进行的胜率评估描述为“平衡已达标”。记录按幕通关率、平均失血、每回合有效伤害、格挡、抽牌、额外能量、稀有核心出现率、无限流发生率和造成的行动次数。
- 原版强度应为定性与多种基线共同参考；避免凭一次卡面数值就断言“与原版平衡”。

## H. 开发路线与验收标准（Codex 执行）

**Phase 0 — 保留既有仓库**：检视 `main`、未合并PR、版本、工具链及游戏路径；保护用户修改，禁止直接覆盖已有成果。先审核并记录基线，不必为了规划重建新仓库。

**Phase 1 — 机制内核**：角色模型/被动、一次回合换牌、卡牌标签、真实/镜像生命、镜中人、反伤事件、额外能量与回合记录器、欲望减费/不叠加、生命支付边界。建立独立单元测试及本地运行日志。

**Phase 2 — 可玩垂直切片**：4基础牌定义+10张起始卡；至少12张奖励卡横跨三体系（其中包含全部5欲望牌、镜中人、魔力之巅），1初始遗物；用占位图实测能进入单人战斗并完成数场战斗。优先检验核心机制而非卡图数量。

**Phase 3 — 全奖励卡池**：完整实现85奖励牌、2古代牌、9遗物、3药水；逐项编译与测试，开发者控制台验证；所有描述与实际效果一致；不得只创建空壳类、只有 UI 而没有效果。

**Phase 4 — 全美术与本地化**：建立确认过的角色设定图、卡牌模板、约91张卡图、遗物与药水图标、能力图标、角色立绘、模型待机与必要 VFX。简中/英文翻译均能正常展示；逐张检查升级文本、动态数值和 UI 裁切。

**Phase 5 — 完整游玩与测试**：起始牌组、多幕整局、死亡、重开、存档/加载、商店、奖励、随机转化、古代升级、卡牌移除、怪物多段攻击、联机隔离与版本回退。未经实际 Windows 测试不可宣称 Windows 完全兼容。

**Phase 6 — 发布准备**：填写版本、依赖、许可证、Steam 创意工坊图与使用说明；输出发布清单和风险。未经用户明确批准不得公开发布或自动合并主分支。

### 工程管理与交付检查

- 按现有 `scripts/dev-macos.sh` 运行 `check`/`build`/`pack`；提交前必须在当前项目版本实际执行并记录结果。
- 每个可验证阶段使用独立 Git 分支/PR；维护已有 `LEARNING_SYNC.md` 与简短开发变更记录，不生成大量重复治理文档。
- 每张卡建立定义 ID、代码类、资源路径、中文名、英文名、升级文本、对应测试用例和当前实现状态（待开发/已编译/已实测/已美术验收）。建议用数据驱动清单，避免85张手工状态散落各处。
- 对当前 v0.111.1 的实际程序集签名优先查 `sts2.dll` 和已安装 BaseLib；不可凭猜测使用 Harmony 或不存在的 API。
- 机器可以自动执行的日常实现/调试无需反复确认；**核心设定、改变五张欲望牌、改变镜中人逆转语义、删减卡池规模、破坏性操作、对外发布**必须提交选项和理由给用户批准。
